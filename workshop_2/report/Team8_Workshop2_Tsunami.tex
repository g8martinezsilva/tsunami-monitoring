    \chapter*{Abstract}
    \addcontentsline{toc}{chapter}{Abstract}
    This report presents the first working version of the medallion architecture of the Team~8 tsunami monitoring system.
The stack runs locally with Docker Compose: Apache Airflow 2.10 with its own metadata database, and a PostgreSQL/PostGIS database that holds the canonical model designed in Workshop~1.
A Bronze DAG, written with the TaskFlow API, performs the historical load of the four sources (NOAA HazEL, USGS FDSN one year per task, and a snapshot of the USGS real-time and NTWC/PTWC feeds), validates every saved file and writes a run manifest.
A Silver DAG, started by a FileSensor when a new Bronze run arrives, cleans the raw files into four Parquet topics (earthquakes, tsunami events, bulletins and rejected records) and loads them idempotently into the database.
The reported full 2010--2025 load contains 2,612 earthquakes, 221 tsunami events and two bulletins, with one non-earthquake catalog record quarantined and no duplicate canonical observations after three loads.
The saved tsunami Parquet files independently confirm stable observations across three processing runs; the exploration also distinguishes catalog validity classes and describes the association between reported earthquake magnitude and maximum water height.

\section{Workshop Scope}
Workshop~2 turns the Workshop~1 data contract~\cite{workshop1} into running code.
The course project assigns it the architecture, the Docker stack, the database schema and the historical ingestion with validation and quarantine; the Workshop~2 guide organizes this work as the Bronze and Silver layers of a medallion architecture orchestrated by Airflow.
Incremental ingestion with watermarks and scheduling belongs to Workshop~3, so the Bronze DAG is triggered manually.
The command-line entry point \texttt{ingest.py -{}-mode historical} downloads Bronze data; normalization, Parquet generation and PostgreSQL persistence are performed by the Silver Airflow DAG. The CLI alone does not perform the complete database load required by the common project contract.

\textbf{Deliverables.} The implementation is in the project repository (branch \path{feat/workshop2-historical-ingestion}): \path{compose.yaml} and \path{airflow/} (Docker stack), \path{airflow/dags/bronze_ingestion_dag.py} and \path{airflow/dags/silver_processing_dag.py}, the shared code in \path{src/}, the schema in \path{sql/}, Bronze and Silver samples in \path{datalake_bronze/samples/} and \path{datalake_silver/samples/}, and the notebook \path{notebooks/02_silver_exploration.ipynb}; the main \path{README.md} explains how to run the pipeline.

\section{Technology Choices}
\begin{itemize}[nosep]
  \item \textbf{Apache Airflow}~\cite{airflow}: the orchestrator used in the course; it provides retries, logs, a web UI as evidence of each run, dynamic task mapping (one task per USGS year) and the FileSensor that links the two layers.
  \item \textbf{Docker Compose}~\cite{compose}: the whole stack starts with one command on any team laptop, and the data folders are mounted from the host so that outputs survive container restarts.
  \item \textbf{PostgreSQL with PostGIS}~\cite{postgis}: a relational model with constraints on uniqueness per source, domain-row type and coordinate ranges, and spatial types for the later geographic analysis. The loader writes each event with its corresponding domain row; the foreign keys alone do not require every event to have a detail row.
  \item \textbf{pandas}~\cite{pandas}: the samples are small (about 3,000 records per full load), pandas is already in the Airflow image and was used for profiling in Workshop~1, and its nullable types (\texttt{Int64}, \texttt{boolean}) keep missing values missing.
  \item \textbf{Apache Parquet}~\cite{parquet}: a columnar format that stores the data types and time zones, compresses well (a full Silver run takes 0.4~MB against 1~MB of raw Bronze files) and can be read directly by pandas and PySpark in Workshop~3.
\end{itemize}

\section{File Nomenclature}
\begin{itemize}[nosep]
  \item \textbf{Bronze:} \texttt{source[\_part]\_YYYYMMDD\_HHMMSS.ext}, for example \path{usgs_fdsn_2011_20261117_001544.csv} or \path{noaa_hazel_page2_20261117_001544.json}; the timestamp is the logical date of the Bronze run, and the extension keeps the source format. Each run also writes \path{bronze_manifest_YYYYMMDD_HHMMSS.json} with its files and record counts.
  \item \textbf{Silver:} \texttt{topic\_YYYYMMDD\_HHMMSS.parquet} with the topics \texttt{earthquakes}, \texttt{tsunami\_events}, \texttt{tsunami\_bulletins} and \texttt{rejected\_records}; the timestamp is the logical date of the Silver run. Each run writes \path{silver_manifest_YYYYMMDD_HHMMSS.json}.
  \item \textbf{Traceability:} every Silver row stores its Bronze file, its record locator (row, item or feature) and the Bronze manifest, and each Silver manifest names the Bronze manifest it came from.
\end{itemize}

\chapter{Methodology}
\label{ch:methodology}

\section{Preprocessing Pipeline (Bronze to Silver)}
\subsection{Missing Values}
Missing values are kept as missing (\texttt{NULL}) and are never imputed: the gaps found in Workshop~1 are real absences in the sources, not errors, so imputing a mean would invent information.
\begin{itemize}[nosep]
  \item \textbf{HazEL:} time of day missing in 23 events (date only) and seconds in 32: kept with a \texttt{time\_precision} flag; coordinates missing in 9 events: kept, without a map point; \texttt{warningStatusId} missing in 76.5\%; \texttt{eqMagnitude} and \texttt{eqDepth} missing in 15.8\% (non-earthquake or unknown cause codes); \texttt{maxWaterHeight} missing in 5.4\%. An unknown cause does not establish a non-seismic origin.
  \item \textbf{USGS:} \texttt{tsunami\_bulletin\_flag} exists only in the real-time feed (null for the 1,929 catalog rows); empty uncertainty columns such as \texttt{magError} are not carried into Silver.
  \item \textbf{Rejected records:} explicit source-specific checks remove unusable observations and record the reason and Bronze locator; the implemented checks and their limits are described below.
\end{itemize}
\subsection{Data Types and Units}
USGS and CAP timestamps are normalized to UTC from ISO~8601 strings or epoch milliseconds. HazEL JSON supplies date and clock components without an explicit time zone; interpreting its complete times as UTC is a normalization assumption that still needs source confirmation. Incomplete NOAA times retain their available precision without an invented full timestamp.
Coordinates are WGS84 decimal degrees with longitudes normalized to $-180$ to $180$.
Magnitudes and depths are floats; the magnitude type is a separate string.
NOAA codes (cause, validity, region, warning status) and hour and minute are nullable integers, and flags are nullable booleans.
Depth is in km (USGS and HazEL), maximum water height in m, and CAP depth text is converted to km only when the unit ``kilometers'' is explicit.
\subsection{Validation and Quarantine}
FDSN records are rejected for a missing identifier or a non-earthquake type; earthquake validation also rejects a missing parsed origin time or magnitude and out-of-range coordinates. HazEL checks for an identifier, a date and coordinate ranges, allowing incomplete clock times and null coordinates. CAP checks for an identifier and an \texttt{info} element. These checks are source-specific; CAP does not receive the earthquake coordinate/time validation.
Explicitly rejected records are written to the \texttt{rejected\_records} Parquet topic and loaded into \texttt{rejected\_record} with their source, identifier, reason and Bronze locator. Conversion or parsing errors outside these checks can interrupt preprocessing; universal quarantine of malformed values is not implemented.
The Silver flag \texttt{expires\_before\_sent} preserves the NTWC expiration inconsistency from Workshop~1. PostgreSQL stores \texttt{sent\_at} and \texttt{expires\_at}, from which it can be derived, but has no dedicated flag column.
\subsection{Outliers}
Earthquake depths and tsunami maximum water heights are checked with the interquartile-range rule: a value outside $[Q_1 - 1.5\,\mathrm{IQR},\ Q_3 + 1.5\,\mathrm{IQR}]$ is flagged in a boolean column, and no value is removed.
The rule was chosen over the Z-score because the distributions are strongly skewed, so the mean and standard deviation are dominated by the extremes.
The reported full run flags 385 of 2,612 earthquake depths ($Q_1 = 10$~km, $Q_3 = 61$~km), consistent with the presence of intermediate and deep earthquakes in Pacific subduction zones; the flag alone does not verify an individual value.
Thirty-three tsunami water heights are flagged ($Q_1 = 0.08$~m, $Q_3 = 0.70$~m), including the 39.3~m of Tohoku 2011 and the 481~m run-up of Tracy Arm 2025~\cite{tracy}.
The flags are therefore kept as information for the analysis rather than as errors.
\subsection{Deduplication}
Within a Silver run, duplicates are removed by (\texttt{source}, \texttt{external\_id}), keeping the most recent \texttt{updated} value for earthquakes, and by CAP \texttt{identifier} for bulletins.
Across runs, the database key \texttt{UNIQUE(source, external\_id)} supports upserts, and a SHA-256 hash of selected normalized fields controls whether a record is rewritten. Changes to fields outside that hash do not trigger an update by themselves.
The same earthquake reported by the FDSN catalog and by the real-time feed stays as two observations; linking them is the cross-source matching of Workshop~3.

\section{Database Schema}
\path{sql/01_schema.sql} creates the Workshop~1 model: \texttt{source}, \texttt{ingestion\_run}, \texttt{ingestion\_state}, \texttt{rejected\_record}, \texttt{event}, \texttt{event\_group}, \texttt{event\_relation}, the domain tables \texttt{earthquake}, \texttt{tsunami\_event} and \texttt{tsunami\_bulletin}, and the four NOAA code catalogs.
The constraints encode the mapping rules: \texttt{UNIQUE(source, external\_id)}; a composite foreign key that only lets an event have the detail row of its own type; checks on coordinate ranges, event types, severity scales, relation types and review statuses; and a PostGIS point column computed from latitude and longitude, with a spatial index.
\path{sql/02_reference_data.sql} inserts the five sources and the NOAA code catalogs (12 causes, 6 validity codes, 23 regions and 6 warning statuses), generated from the configuration and the saved descriptor files.
Both scripts are safe to run again and are executed automatically when the database volume is created.

\section{Docker Stack}
\path{compose.yaml} defines six services on one Docker network:
\begin{itemize}[nosep]
  \item \texttt{db}: PostGIS 16-3.7 with the project database, published only on \texttt{127.0.0.1:5433}; \path{sql/} is mounted as its initialization folder.
  \item \texttt{airflow-db}: PostgreSQL~16 for the Airflow metadata, separate from the project data.
  \item \texttt{airflow-init}: one-off job that migrates the metadata database and creates the admin user.
  \item \texttt{airflow-webserver} (UI on \texttt{127.0.0.1:8080}), \texttt{airflow-scheduler} and \texttt{airflow-triggerer}, with the LocalExecutor.
\end{itemize}
The Airflow image is built from \texttt{apache/airflow:2.10.4} with \path{airflow/requirements.txt}.
The DAG, log and plugin folders, the three \path{datalake_*} folders, \path{src/}, \path{config/} and \texttt{ingest.py} are mounted from the host, so DAG changes are reloaded live and outputs persist.
Credentials and settings come from \path{.env} (template \path{.env.example}); the project database is exposed to the DAGs as the Airflow connection \texttt{tsunami\_db}.
The stack is started with \texttt{docker compose up -d} (Appendix~\ref{app:reproduce}).

\section{Airflow DAGs}
\subsection{Bronze Ingestion DAG}
\texttt{bronze\_ingestion} has the parameters \texttt{start} and \texttt{end} (default 2010-01-01 to 2025-12-31) and these tasks:
\begin{itemize}[nosep]
  \item \texttt{extract\_noaa\_hazel}: downloads every HazEL page and checks that the count equals \texttt{totalItems}.
  \item \texttt{plan\_years} and \texttt{extract\_usgs\_fdsn}: one mapped task per year (16 for the full period), each checked against the USGS \texttt{count} method, so a failed year is retried alone.
  \item \texttt{extract\_feed}: one mapped task each for the USGS real-time feed, NTWC and PTWC, including the CAP messages.
  \item \texttt{validate}: runs even if an extraction failed and checks every saved file (HazEL JSON structure, GeoJSON features, required CSV columns, well-formed XML).
  \item \texttt{persist\_manifest}: writes the JSON manifest; if there was any problem the run is marked as failed, otherwise it writes the arrival marker for the Silver DAG.
\end{itemize}
Downloads use three attempts with waits of 2 and 4~s, each task has two Airflow retries, and all messages go through the logging module into the Airflow task logs.
The schedule is manual (\texttt{schedule=None}); the recorded runs take about 10~seconds. Each full-run manifest enumerates 23 input data files (2 HazEL JSON pages, 16 FDSN CSV files, 1 GeoJSON feed and 4 Atom/CAP XML files), about 1~MB in total; the manifest is an additional file, and the arrival marker is stored separately in \path{_new/}.
\subsection{Silver Processing DAG}
\texttt{silver\_processing} runs every 10~minutes with these tasks:
\begin{itemize}[nosep]
  \item \texttt{wait\_for\_bronze}: a FileSensor on \path{datalake_bronze/_new/bronze_manifest_*.json} with \texttt{poke\_interval} = 60~s, \texttt{timeout} = 9~minutes, \texttt{mode="reschedule"} (the worker slot is freed between checks) and \texttt{soft\_fail=True} (no new data ends as skipped). \texttt{max\_active\_runs=1} prevents overlapping runs.
  \item \texttt{find\_new\_bronze\_runs}: lists the pending markers.
  \item \texttt{bronze\_to\_silver}: applies the preprocessing of Section~\ref{ch:methodology} and writes the four Parquet topics and the Silver manifest.
  \item \texttt{load\_to\_database}: loads them into PostGIS, with one transaction per source.
  \item \texttt{clear\_markers}: removes the markers only after a successful load.
\end{itemize}
The marker is a small file written by the Bronze DAG after a validated run; the Bronze files themselves are never modified.
\subsection{Idempotency}
Re-executing a Bronze run replaces its own files under the same logical timestamp. Its marker remains pending until the database load succeeds, allowing retries after failure. Upserts on \texttt{(source, external\_id)} prevent duplicate canonical observations; rejection deduplication applies per Bronze file. Chapter~\ref{ch:results} distinguishes the reported repeated-load results from the independently verified Silver consistency.

\section{Pipeline Evidence}
Figures~\ref{fig:bronze-runs} and~\ref{fig:silver-runs} show the successful Airflow runs of both DAGs.
Three Bronze samples (one NOAA page per run, with the run manifests) are kept in \path{datalake_bronze/samples/}, and three Silver samples (the \texttt{tsunami\_events} file of each run, with the Silver manifests) in \path{datalake_silver/samples/}; Appendix~\ref{app:samples} shows excerpts.
Each saved Bronze page contains 21 of the 221 observations. The Silver manifests declare the full output counts, but their linked Bronze runs and the other three Parquet topics are not included in these sample folders. The archived samples therefore verify the tsunami outputs and their consistency, while the complete database counts, rejection details and repeated-load results cannot be independently reconstructed from the samples alone.

\section{Silver Data Exploration}
The notebook \path{notebooks/02_silver_exploration.ipynb} contains 19 code cells, 13 Markdown cells and four visualizations. It reads all three Silver samples with pandas, using one representative snapshot for descriptive analysis:
\begin{itemize}[nosep]
  \item \textbf{Schema:} each file has 221 rows and 28 columns with the types of Table~\ref{tab:silver}; the dates cover 2010-01-02 to 2025-12-12.
  \item \textbf{Missing values:} \texttt{warning\_status\_id} is 76.5\% null, reported earthquake magnitude and depth 15.8\%, full timestamps 14.5\% and coordinates 4.1\%. All 35 missing magnitudes have non-earthquake or unknown cause codes; nulls remain unfilled.
  \item \textbf{Validation:} no missing or duplicated observation keys, out-of-range non-null coordinates, negative measurements or date/precision inconsistencies. Lineage fields are populated and hashes match the SHA-256 format; file availability is checked separately.
  \item \textbf{Outliers:} recomputing the IQR rule gives the same 33 flagged water heights as the pipeline (bounds $-0.85$ to $1.63$~m), with 0 disagreements.
  \item \textbf{Consistency across runs:} the files share the same schema, 221 keys, hashes and stored observation values apart from lineage and processing timestamps. They represent 221 observations, not 663 independent events, and this comparison does not prove PostgreSQL idempotency.
  \item \textbf{Geography and classification:} NOAA region 82 (New Caledonia, New Guinea, Solomon Islands and Vanuatu) contains 56 observations, followed by Japan with 35. Validity codes identify 179 definite, 33 probable and 8 questionable tsunamis, plus 1 erroneous entry retained by Silver; the records are not equally well confirmed. These source-region counts do not apply the separate Marine Regions polygon filter.
\end{itemize}
Figure~\ref{fig:silver-plots} includes 170 complete magnitude/height pairs selected by earthquake-only cause code 1 and probable or definite validity (3--4). Pearson's $r = 0.444$ and Spearman's $\rho = 0.470$ are descriptive associations, not causal or predictive validation. Magnitude is not tsunami severity, and maximum water height can include local run-up rather than open-ocean waves. Reporting gaps, extreme local measurements and the broader catalog's non-earthquake causes limit interpretation.

\chapter{Discussion}
\label{ch:discussion}

\section{Challenges and Decisions}
\begin{itemize}[nosep]
  \item \textbf{Memory:} a 7~GB laptop runs Airflow and two PostgreSQL servers with about 2~GB free; the heavy geographic step of Workshop~1 was therefore kept out of the DAGs for now.
  \item \textbf{FileSensor semantics:} a sensor on the Bronze files themselves would fire repeatedly because old files remain. Arrival markers stay pending until loading succeeds; a failed processing attempt can therefore be retried, with database upserts preventing duplicate canonical observations.
  \item \textbf{Airflow file ownership:} files written in the containers belonged to another user until \texttt{AIRFLOW\_UID} was set to the host user.
  \item \textbf{Missing connection:} the FileSensor needs a filesystem connection that Airflow does not create by default; it is now defined in \path{compose.yaml}.
  \item \textbf{Non-earthquake catalog events:} the USGS catalog contains a nuclear explosion within the scope; the type check sends it to quarantine.
\end{itemize}

\chapter{Conclusions and Open Questions}
\label{ch:conclusions}
\section{Results}
Workshop~2 implements the Bronze--Silver--PostgreSQL path, with Docker services, Airflow orchestration, source-specific validation and a canonical database loader. The saved Airflow screenshots record successful runs, and the three tsunami Parquet outputs demonstrate repeatable processing with preserved missing values, time precision, units and source identifiers.
The exploration verifies stable observations across runs while distinguishing catalog validity and statistical outliers. Its magnitude/height association remains descriptive. The reported database results are retained separately from the independently reproducible Silver findings, with the evidence limits described in Chapter~\ref{ch:results}.

\section{Open Questions for Workshop 3}
The next academic stage addresses incremental polling, watermarks, reconciliation and reviewed cross-source event identification. Gold aggregates and the Pacific scope classification support the later temporal/geographic analysis and monitoring dashboard; they are not presented as Workshop~2 results.

\chapter{Reflection}
\label{ch:reflection}
\textbf{What worked.} Building on the Workshop~1 contract made the implementation direct: the sources, keys, units and cleaning rules were already decided and documented, so each DAG task maps to a written rule. Reusing one \path{src/} package for the command-line tool and the DAGs avoided two versions of the same code.

\textbf{What was difficult.} Most of the effort went into the environment rather than the code: Docker and Airflow configuration, file permissions, connections and the memory limits of the laptops. Coordinating three people on one branch also required clear rules on who edits which files.

\textbf{Lessons learned.} Test each piece in the real environment as early as possible, keep raw data immutable and add metadata (manifests and markers) around it instead, and prove idempotency by running the same load more than once.

\begin{lstlisting}
cp .env.example .env          # then change the passwords
docker compose up -d          # PostGIS, Airflow metadata DB and Airflow services
docker compose ps             # all services running; UI at http://localhost:8080

Within ten minutes the Silver DAG processes the new Bronze run. The outputs can be inspected with:
\begin{lstlisting}
ls datalake_bronze datalake_silver
docker exec tsunami-postgres sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select * from ingestion_run"'
docker compose down           # stop; data stay in the Docker volumes and folders
\end{lstlisting}
