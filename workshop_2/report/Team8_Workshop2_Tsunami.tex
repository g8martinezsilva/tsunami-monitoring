    \chapter*{Abstract}
    \addcontentsline{toc}{chapter}{Abstract}
    This report presents the first working version of the medallion architecture of the Team~8 tsunami monitoring system.
The stack runs locally with Docker Compose: Apache Airflow 2.10 with its own metadata database, and a PostgreSQL/PostGIS database that holds the canonical model designed in Workshop~1.
A Bronze DAG, written with the TaskFlow API, performs the historical load of the four sources (NOAA HazEL, USGS FDSN one year per task, and a snapshot of the USGS real-time and NTWC/PTWC feeds), validates every saved file and writes a run manifest.
A Silver DAG, started by a FileSensor when a new Bronze run arrives, cleans the raw files into four Parquet topics (earthquakes, tsunami events, bulletins and rejected records) and loads them idempotently into the database.
The full 2010--2025 load produces 2,612 earthquakes, 221 tsunami events and the current bulletins; one catalog record, a 2017 nuclear explosion, is quarantined, and repeated runs add no duplicate rows.

\section{Technology Choices}
\begin{itemize}[nosep]
  \item \textbf{Apache Airflow}~\cite{airflow}: the orchestrator used in the course; it provides retries, logs, a web UI as evidence of each run, dynamic task mapping (one task per USGS year) and the FileSensor that links the two layers.
  \item \textbf{Docker Compose}~\cite{compose}: the whole stack starts with one command on any team laptop, and the data folders are mounted from the host so that outputs survive container restarts.
  \item \textbf{PostgreSQL with PostGIS}~\cite{postgis}: a relational model with constraints that enforce the Workshop~1 rules (uniqueness per source, one detail row per event type, coordinate ranges) and spatial types for the later geographic analysis.
  \item \textbf{pandas}~\cite{pandas}: the samples are small (about 3,000 records per full load), pandas is already in the Airflow image and was used for profiling in Workshop~1, and its nullable types (\texttt{Int64}, \texttt{boolean}) keep missing values missing.
  \item \textbf{Apache Parquet}~\cite{parquet}: a columnar format that stores the data types and time zones, compresses well (a full Silver run takes 0.4~MB against 1~MB of raw Bronze files) and can be read directly by pandas and PySpark in Workshop~3.
\end{itemize}

\section{File Nomenclature}
\begin{itemize}[nosep]
  \item \textbf{Bronze:} \texttt{source[\_part]\_YYYYMMDD\_HHMMSS.ext}, for example \path{usgs_fdsn_2011_20261117_001544.csv} or \path{noaa_hazel_page2_20261117_001544.json}; the timestamp is the logical date of the Bronze run, and the extension keeps the source format. Each run also writes \path{bronze_manifest_YYYYMMDD_HHMMSS.json} with its files and record counts.
  \item \textbf{Silver:} \texttt{topic\_YYYYMMDD\_HHMMSS.parquet} with the topics \texttt{earthquakes}, \texttt{tsunami\_events}, \texttt{tsunami\_bulletins} and \texttt{rejected\_records}; the timestamp is the logical date of the Silver run. Each run writes \path{silver_manifest_YYYYMMDD_HHMMSS.json}.
  \item \textbf{Traceability:} every Silver row stores its Bronze file, its record locator (row, item or feature) and the Bronze manifest, and each Silver manifest names the Bronze manifest it came from.
\end{itemize}

\chapter{Methodology}
\label{ch:methodology}

\section{Preprocessing Pipeline (Bronze to Silver)}
\subsection{Missing Values}
Missing values are kept as missing (\texttt{NULL}) and are never imputed: the gaps found in Workshop~1 are real absences in the sources, not errors, so imputing a mean would invent information.
\begin{itemize}[nosep]
  \item \textbf{HazEL:} time of day missing in 23 events (date only) and seconds in 32: kept with a \texttt{time\_precision} flag; coordinates missing in 9 events: kept, without a map point; \texttt{warningStatusId} missing in 76.5\%; \texttt{eqMagnitude} and \texttt{eqDepth} missing in 15.8\% (non-seismic tsunamis); \texttt{maxWaterHeight} missing in 5.4\%.
  \item \textbf{USGS:} \texttt{tsunami\_bulletin\_flag} exists only in the real-time feed (null for the 1,929 catalog rows); empty uncertainty columns such as \texttt{magError} are not carried into Silver.
  \item \textbf{Dropped records:} only records that cannot be identified or placed in time (no identifier, no origin time, no magnitude) are removed, and they go to quarantine instead of being deleted silently.
\end{itemize}
\subsection{Data Types and Units}
Times are converted to UTC \texttt{datetime} values: ISO~8601 strings (FDSN), epoch milliseconds (real-time feed), ISO~8601 with offset (CAP) and the six HazEL date columns.
Coordinates are WGS84 decimal degrees with longitudes normalized to $-180$ to $180$.
Magnitudes and depths are floats; the magnitude type is a separate string.
NOAA codes (cause, validity, region, warning status) and hour and minute are nullable integers, and flags are nullable booleans.
Depth is in km (USGS and HazEL), maximum water height in m, and CAP depth text is converted to km only when the unit ``kilometers'' is explicit.
\subsection{Validation and Quarantine}
Records are rejected when the identifier, the origin time or date, or the magnitude (earthquakes) is missing, when a coordinate is out of range, or when a USGS catalog record is not an earthquake.
Rejected records are written to the \texttt{rejected\_records} Parquet topic and to the \texttt{rejected\_record} table with the source, identifier, reason and Bronze locator, and never stop the batch.
Inconsistencies inside a valid record are flagged and preserved, not corrected: for example \texttt{expires\_before\_sent} marks the NTWC message whose \texttt{expires} is 11~hours before \texttt{sent} (problem~8 of Workshop~1).
\subsection{Outliers}
Numeric fields are checked with the interquartile-range rule: a value outside $[Q_1 - 1.5\,\mathrm{IQR},\ Q_3 + 1.5\,\mathrm{IQR}]$ is flagged in a boolean column, and no value is removed.
The rule was chosen over the Z-score because the distributions are strongly skewed, so the mean and standard deviation are dominated by the extremes.
In a full run, 385 of 2,612 earthquake depths are flagged ($Q_1 = 10$~km, $Q_3 = 61$~km): they are real intermediate and deep earthquakes of the Pacific subduction zones.
Thirty-three tsunami water heights are flagged ($Q_1 = 0.08$~m, $Q_3 = 0.70$~m), including the 39.3~m of Tohoku 2011 and the 481~m run-up of Tracy Arm 2025, both documented real events.
The flags are therefore kept as information for the analysis rather than as errors.
\subsection{Deduplication}
Within a Silver run, duplicates are removed by (\texttt{source}, \texttt{external\_id}), keeping the most recent \texttt{updated} value for earthquakes, and by CAP \texttt{identifier} for bulletins.
Across runs, the database key \texttt{UNIQUE(source, external\_id)} makes every load an upsert, and a SHA-256 content hash of the normalized fields means that a record is rewritten only when its content changes.
The same earthquake reported by the FDSN catalog and by the real-time feed stays as two observations; linking them is the cross-source matching of Workshop~3.

\section{Database Schema}
\path{sql/01_schema.sql} creates the Workshop~1 model: \texttt{source}, \texttt{ingestion\_run}, \texttt{ingestion\_state}, \texttt{rejected\_record}, \texttt{event}, \texttt{event\_group}, \texttt{event\_relation}, the domain tables \texttt{earthquake}, \texttt{tsunami\_event} and \texttt{tsunami\_bulletin}, and the four NOAA code catalogs.
The constraints encode the mapping rules: \texttt{UNIQUE(source, external\_id)}; a composite foreign key that only lets an event have the detail row of its own type; checks on coordinate ranges, event types, severity scales, relation types and review statuses; and a PostGIS point column computed from latitude and longitude, with a spatial index.
\path{sql/02_reference_data.sql} inserts the five sources and the NOAA code catalogs (12 causes, 6 validity codes, 23 regions and 6 warning statuses), generated from the configuration and the saved descriptor files.
Both scripts are safe to run again and are executed automatically when the database volume is created.

\section{Docker Stack}
\path{compose.yaml} defines six services on one Docker network:
\begin{itemize}[nosep]
  \item \texttt{db}: PostGIS 16-3.7 with the project database, published only on \texttt{127.0.0.1:5433}; \path{sql/} is mounted as its initialization folder.
  \item \texttt{airflow-db}: PostgreSQL~16 for the Airflow metadata, separate from the project data.
  \item \texttt{airflow-init}: one-off job that migrates the metadata database and creates the admin user.
  \item \texttt{airflow-webserver} (UI on \texttt{127.0.0.1:8080}), \texttt{airflow-scheduler} and \texttt{airflow-triggerer}, with the LocalExecutor.
\end{itemize}
The Airflow image is built from \texttt{apache/airflow:2.10.4} with \path{airflow/requirements.txt}.
The DAG, log and plugin folders, the three \path{datalake_*} folders, \path{src/}, \path{config/} and \texttt{ingest.py} are mounted from the host, so DAG changes are reloaded live and outputs persist.
Credentials and settings come from \path{.env} (template \path{.env.example}); the project database is exposed to the DAGs as the Airflow connection \texttt{tsunami\_db}.
The stack is started with \texttt{docker compose up -d} (Appendix~\ref{app:reproduce}).

\section{Airflow DAGs}
\subsection{Bronze Ingestion DAG}
\texttt{bronze\_ingestion} has the parameters \texttt{start} and \texttt{end} (default 2010-01-01 to 2025-12-31) and these tasks:
\begin{itemize}[nosep]
  \item \texttt{extract\_noaa\_hazel}: downloads every HazEL page and checks that the count equals \texttt{totalItems}.
  \item \texttt{plan\_years} and \texttt{extract\_usgs\_fdsn}: one mapped task per year (16 for the full period), each checked against the USGS \texttt{count} method, so a failed year is retried alone.
  \item \texttt{extract\_feed}: one mapped task each for the USGS real-time feed, NTWC and PTWC, including the CAP messages.
  \item \texttt{validate}: runs even if an extraction failed and checks every saved file (HazEL JSON structure, GeoJSON features, required CSV columns, well-formed XML).
  \item \texttt{persist\_manifest}: writes the JSON manifest; if there was any problem the run is marked as failed, otherwise it writes the arrival marker for the Silver DAG.
\end{itemize}
Downloads use three attempts with waits of 2 and 4~s, each task has two Airflow retries, and all messages go through the logging module into the Airflow task logs.
The schedule is manual (\texttt{schedule=None}); a full run takes about 10~seconds and saves 24 files (about 1~MB).
\subsection{Silver Processing DAG}
\texttt{silver\_processing} runs every 10~minutes with these tasks:
\begin{itemize}[nosep]
  \item \texttt{wait\_for\_bronze}: a FileSensor on \path{datalake_bronze/_new/bronze_manifest_*.json} with \texttt{poke\_interval} = 60~s, \texttt{timeout} = 9~minutes (shorter than the schedule, so runs do not overlap), \texttt{mode="reschedule"} (the worker slot is freed between checks) and \texttt{soft\_fail=True} (a period without new Bronze data ends as skipped, not failed).
  \item \texttt{find\_new\_bronze\_runs}: lists the pending markers.
  \item \texttt{bronze\_to\_silver}: applies the preprocessing of Section~\ref{ch:methodology} and writes the four Parquet topics and the Silver manifest.
  \item \texttt{load\_to\_database}: loads them into PostGIS, with one transaction per source.
  \item \texttt{clear\_markers}: removes the markers only after a successful load.
\end{itemize}
The marker is a small file written by the Bronze DAG after a validated run; the Bronze files themselves are never modified.
\subsection{Idempotency}
Bronze file names use the run's logical date, so re-running the same Bronze run overwrites its own files instead of creating new ones.
A Bronze run is processed by Silver only while its marker exists, and the marker is removed only after the database load succeeds, so a failure leaves it pending for the next Silver run.
The database load is an upsert on \texttt{(source, external\_id)} that rewrites a row only when its content hash changes, and a rejected record is quarantined only once per Bronze file.
As a result, loading the same historical data three times produced the same database content (Section~\ref{ch:results}).

\section{Silver Data Exploration}
The notebook \path{notebooks/02_silver_exploration.ipynb} reads the three \texttt{tsunami\_events} Silver samples with pandas and checks them without modifying them:
\begin{itemize}[nosep]
  \item \textbf{Schema:} each file has 221 rows and 28 columns with the types of Table~\ref{tab:silver}; the dates cover 2010-01-02 to 2025-12-12.
  \item \textbf{Missing values:} kept as missing, as designed: \texttt{warning\_status\_id} 76.5\%, \texttt{reported\_eq\_magnitude} and \texttt{reported\_eq\_depth} 15.8\% (all 35 belong to tsunamis without an earthquake cause), incomplete timestamps 14.5\% and coordinates 4.1\%.
  \item \textbf{Validation:} no duplicated (\texttt{source}, \texttt{external\_id}) keys, no out-of-range coordinates, no negative measurements, no inconsistency between \texttt{event\_time}, \texttt{event\_date} and \texttt{time\_precision}, and complete lineage fields with valid SHA-256 hashes.
  \item \textbf{Outliers:} recomputing the IQR rule gives the same 33 flagged water heights as the pipeline (bounds $-0.85$ to $1.63$~m), with 0 disagreements.
  \item \textbf{Consistency across runs:} the three Silver runs have the same schema, the same 221 keys and 0 different content hashes, which confirms that repeated processing of the same historical data is stable.
\end{itemize}

\chapter{Discussion}
\label{ch:discussion}

\section{Challenges and Decisions}
\begin{itemize}[nosep]
  \item \textbf{Memory:} a 7~GB laptop runs Airflow and two PostgreSQL servers with about 2~GB free; the heavy geographic step of Workshop~1 was therefore kept out of the DAGs for now.
  \item \textbf{FileSensor semantics:} a sensor on the Bronze files themselves would fire on every run, because old files remain. Arrival markers that Silver removes after loading make each Bronze run trigger exactly one Silver processing.
  \item \textbf{Airflow file ownership:} files written in the containers belonged to another user until \texttt{AIRFLOW\_UID} was set to the host user.
  \item \textbf{Missing connection:} the FileSensor needs a filesystem connection that Airflow does not create by default; it is now defined in \path{compose.yaml}.
  \item \textbf{Non-earthquake catalog events:} the USGS catalog contains a nuclear explosion within the scope; the type check sends it to quarantine.
\end{itemize}

\chapter{Conclusions and Open Questions}
\label{ch:conclusions}
\section{Results}
The medallion pipeline works end to end: the Docker stack starts with one command, the Bronze DAG loads the full 2010--2025 history of the four sources with validation and a manifest, and the Silver DAG turns each new Bronze run into typed Parquet files and an idempotent database load with quarantine.
The Workshop~1 cleaning rules (UTC times, partial NOAA times, explicit units, flags instead of corrections) are now enforced in code and by database constraints.

\section{Open Questions for Workshop 3}
\begin{itemize}[nosep]
  \item Schedule the incremental ingestion (USGS feed every minute at most, tsunami.gov every 5 minutes) with watermarks and the FDSN reconciliation query.
  \item Add the Pacific scope flags (Marine Regions and 100~km margin) with a memory-efficient method.
  \item Implement the cross-source matching and the review of \texttt{event\_relation} candidates.
  \item Build the Gold layer from the Silver Parquet files with PySpark.
  \item Add automated tests that use the recorded fixtures in \path{tests/fixtures/}.
\end{itemize}

\chapter{Reflection}
\label{ch:reflection}
\textbf{What worked.} Building on the Workshop~1 contract made the implementation direct: the sources, keys, units and cleaning rules were already decided and documented, so each DAG task maps to a written rule. Reusing one \path{src/} package for the command-line tool and the DAGs avoided two versions of the same code.

\textbf{What was difficult.} Most of the effort went into the environment rather than the code: Docker and Airflow configuration, file permissions, connections and the memory limits of the laptops. Coordinating three people on one branch also required clear rules on who edits which files.

\textbf{Lessons learned.} Test each piece in the real environment as early as possible, keep raw data immutable and add metadata (manifests and markers) around it instead, and prove idempotency by running the same load more than once.

\chapter{Reproducing the Workshop 2 Results}
\label{app:reproduce}
From the repository root, on a machine with Docker:
\begin{lstlisting}
cp .env.example .env          # then change the passwords
docker compose up -d          # PostGIS, Airflow metadata DB and Airflow services
docker compose ps             # all services running; UI at http://localhost:8080
\end{lstlisting}
In the Airflow UI, unpause \texttt{silver\_processing} and trigger \texttt{bronze\_ingestion} (optionally with another \texttt{start} and \texttt{end}).
Within ten minutes the Silver DAG processes the new Bronze run. The outputs can be inspected with:
\begin{lstlisting}
ls datalake_bronze datalake_silver
docker exec tsunami-postgres sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select * from ingestion_run"'
docker compose down           # stop; data stay in the Docker volumes and folders
\end{lstlisting}
